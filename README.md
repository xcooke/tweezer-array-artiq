This code accesses a sipyco server generated by `tweezer-array` repo on a pc that has the SLM and camera plugged into.

# Running server

Follow instructions in `tweezer-array` repo to launch server.

Inside `device_db.py` point to the ip address of the pc that is hosting the server.

When ARTIQ runs a program it can call functions that belong to instantiated classes over the network.

# Phaser frequency

Set centre frequency (duc?) to 100MHz (the centre of the AOM bandwidth).
Do not exceed +-12.5MHz (<87.5MHZ or >112.5MHZ) with the specific AOMs.
Some experiments have this hardcoded, others do not.
There seems to be a bug(?) where when <90MHz or >110MHz the Phaser generates an additional harmonic.

# Files

## Files in use

`tweezer-array\characterise_aom.py` this triggers server to create new AOM characterisation folder, moves AOM tweezer across the accessible camera region while saving camera images to the server. I typically use +-11MHz. After running this follow instructions in `tweezer-array` to generate a AOM calibration file. Previously I used this file in ARTIQ `position_calibration.pkl` to map location->frequency, but for my tetris rearrangement I used it server side.

`tweezer-array/generate_slm_phase.py` this moves the AOM to its 'maximum' range, identifies the coordinates of the tweezer, and finds coordinates to fit a square (and zero rotation) SLM array of points to. Typically I set AOM range here to less than the calibration range so the SLM array are definitely inside what is allowed. I have successfully used +-8MHz to allow for drift against the Fourier calibration. I suspect this can be increased, allowing larger array size. The SLM phase pattern is optimised computationally first server side, and can be optimised experimentally (this is commented out in the driver at the moment). I turned this off because in the experimental optimisation it splits up the image into regions around each tweezer and if the Fourier calibration drifts then the regions are not correct and the optimisation doesn't work. This will therefore work better with sparser arrays.

`tweezer-array/load_slm_camera.py` not a good name. Not currently in use, but I used it to write most of my code. The `run()` function of the experiment is a mess and I suggest ignore it (currently performs the old rearrangement method (and updates the camera each frame), the commented out bit moved tweezer to static tweezer locations. This is old!)

`tweezer-array/rearrange.py` actually does the tetris rearrangement. This is pretty much functional and can be run at speeds more than fast enough to move atoms with AOM tweezers. This code does not take any photos with camera. If you want to see the rearrangement of the atoms uncomment `#camera_hardware.close()` on line 54 of `server.py` in `tweezer-array` repo. This closes the camera after server is turned on and you can then open ThorImageCam (or ThorCam) and view the camera live. Uses DMA. See labbook for details around timing (https://labbook.stronlab.net/2026/2026-09-08-Tetris-algorithm).

`tweezer-array/test.py` a test showing how to synchronise rpc calls.
